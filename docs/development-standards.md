# Luminova 开发规范

> 状态：强制执行  
> 适用范围：整个仓库  
> 目标：用明确的领域模型、稳定的类边界和高质量中文注释，让代码易于理解、扩展、测试和维护。

## 1. 执行原则

- 后续需求默认适用本规范，不需要再次提醒采用 DDD 或添加中文注释。
- 后端 Java 代码块的 `{` 放在语句行尾，`}` 单独占一行。完整排版规则见根目录 [AGENTS.md](../AGENTS.md) 的「代码排版」。前端不套用该规则。
- 新代码必须遵守；修改旧代码时，本次触及的范围必须同步收敛到本规范。
- 不为了形式套用 DDD。纯配置、简单技术适配或无业务规则的模块可以保持简单，但不能把业务规则放进 Controller、Mapper 或 Adapter。
- 发现需求、代码、`GLOSSARY.md` 与本规范互相冲突时，先明确冲突并更新设计，不能自行选择一种含义继续实现。
- 规范无法满足时必须在实现前说明原因、影响和替代方案，取得明确同意后才可偏离。

## 2. 领域语言

### 2.1 统一语言

- 项目领域术语以根目录 [GLOSSARY.md](../GLOSSARY.md) 为准。
- 需求出现新的领域名词时，先给出精确定义，再用于类名、方法名、数据库名和接口文档。
- 同一概念只保留一个规范名称；容易混淆的别名写入词汇表的 `_Avoid_`。
- 词汇表只定义业务概念，不记录 Java、数据库或框架实现细节。

### 2.2 需求建模

实施业务需求前至少明确：

1. 需求属于哪个限界上下文。
2. 哪个聚合维护核心不变量。
3. 一致性和事务边界在哪里。
4. 哪些操作是领域行为，哪些只是应用编排或外部副作用。
5. 需要哪些跨上下文契约，失败和重试语义是什么。
6. 是否产生新的领域术语、事件或不可逆架构决策。

## 3. DDD 架构

### 3.1 标准分层

后端业务模块使用以下依赖方向：

```text
interfaces -> application -> domain
                    |          ^
                    v          |
              port(interface)  |
                    ^          |
                    |          |
             infrastructure ---+
```

只允许依赖指向内层。禁止 domain 反向依赖 application、interfaces 或 infrastructure。

### 3.2 Interfaces 层

负责：

- HTTP、Dubbo、消息等外部协议接入。
- 请求 DTO 校验、协议字段转换、响应 DTO 映射。
- 从可信上下文取得当前用户、请求 ID 等协议信息。

不负责：

- 开启业务事务。
- 直接调用 Mapper、Repository、Redis 或第三方 SDK。
- 编写业务规则、权限规则或复杂流程。
- 返回领域聚合或持久化 Entity。

Controller 应短小，通常只调用一个应用服务入口。若 Controller 需要多步业务判断，应将流程移入应用层。

### 3.3 Application 层

负责：

- 按用例组织流程和事务边界。
- 加载聚合、调用领域行为、保存聚合。
- 协调跨上下文接口和外部端口。
- 将领域结果转换为稳定的应用结果。结构转换使用 MapStruct 的 Converter，不在用例里逐字段拷贝。
- 安排事务提交后的外部副作用。

不负责：

- 把核心业务规则写成大量 `if/else`。
- 直接依赖具体数据库、Redis、Sa-Token 或供应商 SDK。
- 返回框架对象或泄漏领域内部状态。
- 通过应用服务互相调用来复用简单逻辑。

应用服务必须按具体用例命名，例如 `RegisterUserApplicationService`，禁止笼统的 `UserService`。

应用端口接口放在 `application.port.<能力>`，例如 `application.port.login`。用例服务、策略实现、命令和结果留在 `application.<能力>`。端口包只放接口，不放 Spring 组件。领域仓储和领域 seam 仍放在 `domain`，它们的 Adapter 放在 `infrastructure`。

### 3.4 Domain 层

可包含：

- 聚合根、实体、值对象。
- 领域行为、领域事件、领域模块。
- 仓储接口和领域真正需要的 seam。
- 业务异常及不变量。

强制要求：

- 不依赖 Spring、MyBatis、Dubbo、Sa-Token、Redis、HTTP 或供应商 SDK。
- 聚合通过有业务含义的方法改变状态，不公开任意 setter。
- 值对象创建时即验证合法性，创建后保持不可变。
- 跨聚合强一致性必须有明确理由；默认由应用层协调。
- 领域异常表达业务失败，不携带密码、Token、验证码或其他敏感值。

### 3.5 Infrastructure 层

负责：

- Repository、消息、缓存、RPC、文件存储和第三方 SDK 的 Adapter。
- 领域对象与持久化 Entity 的转换。结构转换使用 MapStruct 的 Converter，并走聚合或值对象构造器，不给聚合补 setter。类名以 `Converter` 结尾，不以 `Mapper` 结尾。规则见 [AGENTS.md](../AGENTS.md)。
- 超时、重试、连接池、序列化和技术错误映射。
- 数据库读写使用 MyBatis-Plus 的 `BaseMapper` 和 `LambdaQueryWrapper`，规则见 [AGENTS.md](../AGENTS.md)。

不负责：

- 决定业务是否合法。
- 绕过聚合直接修改业务状态。
- 把 MyBatis-Plus Wrapper、Redis key、供应商 DTO 泄漏到内层。
- 让应用层、领域层或 Controller 直接调用 Mapper。

仓储实现按业务端口命名，放在 infrastructure，不得以 MyBatis 做前缀，例如 `UserAccountRepositoryAdapter`。框架配置类才使用技术名称，例如 `SaTokenSessionAdapter`。

## 4. 聚合、事务与跨上下文

- 每个写用例只能有一个清晰的应用服务入口和事务边界。
- 聚合内部维护必须同步成立的不变量；数据库唯一约束作为并发情况下的最终防线。
- 不在 Controller 中使用 `@Transactional`。
- 事务内避免不可控的远程调用；必须远程调用时明确超时、失败与补偿策略。
- 事务提交后的副作用使用明确的提交后回调、Outbox 或可靠事件机制，不得假设数据库提交一定成功。
- 跨上下文通过防腐层契约协作，只传稳定 ID、值和结果 DTO。
- 业务表只引用稳定的领域主体 ID，不引用手机号、邮箱、昵称等可变外部标识。
- 跨上下文不得共享数据库表、Mapper、持久化 Entity 或聚合对象。

## 5. 模块与接口设计

- 优先设计深模块：小而稳定的接口隐藏复杂实现。
- Interface 必须同时说明参数、结果、不变量、调用顺序、错误模式和性能/重试约束。
- 只有实际存在变化点或至少需要 Fake/Adapter 测试替换时才引入 seam，避免为假想扩展创建大量空接口。
- 调用方和测试通过同一个 Interface 使用模块；测试不应穿透 Interface 了解内部实现。
- 依赖由外部注入，类内部不得随意 `new` 基础设施依赖。
- 优先返回结果，由应用层统一执行副作用。
- 新增设计模式必须解决真实变化点；不得为了“使用设计模式”增加无价值层级。

## 6. 命名规范

- 使用领域词汇命名聚合、实体、值对象和方法。
- 应用服务使用“用例 + ApplicationService”，例如 `ChangePasswordApplicationService`。
- 领域 seam 使用能力名称，例如 `PasswordHasher`、`UserAccountRepository`。
- 基础设施 Adapter 使用“技术 + 能力/接口”，例如 `BCryptPasswordHasher`。
- DTO 必须带方向或用途，例如 `PasswordLoginRequest`、`LoginResponse`、`RegisterUserCommand`。
- 结构转换器以 `Converter` 结尾，例如 `UserAccountPersistenceConverter`。`Mapper` 只留给数据库 `BaseMapper`，禁止把 MapStruct 转换器命名为 `UserAccountMapper`。
- 禁止模糊名称：`CommonUtil`、`BaseManager`、`DataHelper`、`ProcessService`、`UserService`、`AuthService`。
- 方法名称应表达业务行为，例如 `disable(...)`、`bindIdentity(...)`，避免 `updateStatus(...)` 之类弱语义操作。

## 7. 中文注释规范

### 7.1 总体要求

- 新增或修改代码的注释统一使用中文；标准库名称、协议名称和代码标识符保留英文。
- 注释必须准确描述当前实现。错误或过期注释与代码缺陷同等处理。
- 注释解释职责、逻辑边界、业务不变量、设计原因和风险，不逐行翻译语法。
- 不能只写类注释。公开方法，以及含有业务判断、事务、并发或安全取舍的私有方法，都要有方法注释。
- 方法体内只在复杂逻辑处注释。普通方法调用和容易看懂的分支不添加注释。
- 可读性优先依靠准确命名、短方法和值对象，注释用于解释代码不能直接表达的信息。

### 7.2 必须注释

以下位置必须添加中文 Javadoc：

- 聚合根、实体、值对象、领域模块和领域事件。
- 应用服务、端口、仓储接口及 Adapter。
- Controller、RPC Facade 和对外 DTO。
- 所有 `public` 方法及跨模块接口方法。
- 含有业务判断、事务边界、并发控制或安全取舍的私有方法。

以下逻辑必须添加中文说明：

- 聚合维护的不变量和状态转换条件。
- 事务范围、提交后副作用及回滚影响。
- 幂等、乐观锁、分布式锁、Redis Lua 和并发冲突处理。
- 密码恒时校验、验证码消费、Token 撤销、脱敏等安全逻辑。
- 外部调用的超时、重试、幂等性和错误映射。
- 为兼容历史数据或绕开框架限制而采用的非直观实现。

### 7.3 类级 Javadoc 内容

关键类的 Javadoc 必须能回答：

1. 这个类在领域或用例中的职责是什么。
2. 它明确不负责什么。
3. 它维护哪些不变量或调用顺序。
4. 敏感数据、事务、并发或重试有哪些约束。

示例：

```java
/**
 * 手机号密码认证策略。
 *
 * <p>负责验证手机号密码凭证，并将账号上下文返回的结果转换为统一认证主体。
 * 本类不创建登录会话、不读取密码哈希，也不处理 HTTP 响应；会话签发和安全审计
 * 由统一登录应用服务完成。</p>
 *
 * <p>安全约束：异常和日志中不得包含原始密码或完整手机号。</p>
 */
final class PhonePasswordAuthenticator {
}
```

### 7.4 方法 Javadoc 内容

公开业务方法应说明：

- 行为目的和结果。
- 必要的前置条件与不变量。
- 参数的业务含义。
- 可能出现的业务异常。
- 非显而易见的事务或安全影响。

```java
/**
 * 禁用当前用户主体。
 *
 * <p>该方法只改变聚合内的账号状态。全部会话撤销属于聚合外副作用，必须由应用层
 * 在事务成功提交后执行，避免数据库回滚但会话已经失效。</p>
 *
 * @param operatorId 执行操作的管理员用户 ID，不能与当前用户 ID 相同
 * @param reason     去除首尾空格后不能为空的禁用原因
 * @throws CannotDisableSelfException 管理员尝试禁用自己时抛出
 */
public void disable(UserId operatorId, DisableReason reason) {
}
```

### 7.5 禁止的注释

- “获取用户名”“设置状态”“进入 if 判断”等逐行翻译代码的注释。
- 给普通赋值、查询、转换或一眼能看懂的方法调用添加的注释。
- 与实现不一致或保留被注释掉的旧代码。
- 在注释中记录真实密码、验证码、Token、完整手机号、密钥或生产地址。
- 用长篇注释掩盖超大类、含糊命名和错误分层。
- 为满足数量要求复制相同注释。

## 8. 安全与日志

- 密码、验证码、Token、密钥和完整个人标识不得出现在日志、异常、注释或 `toString()` 中。
- 敏感 DTO 和 Entity 必须显式排除 Lombok 自动生成的 `toString()` 内容。
- 认证失败响应不得泄漏账号是否存在、具体状态或哈希信息。
- 权限和账号状态必须在服务端检查，不信任客户端角色和用户 ID。
- 日志只保存脱敏后的个人标识，并带请求 ID 便于审计。
- 安全规则必须有自动化测试，不能只依赖人工检查。

## 9. 测试与自动约束

### 9.1 测试分层

- 领域测试：直接验证聚合、值对象和领域模块的不变量，无 Spring 上下文。
- 应用测试：使用 Fake 端口验证用例编排、事务结果和副作用顺序。
- Adapter 测试：验证 PostgreSQL、Redis、Dubbo、Sa-Token 和第三方适配行为。
- 接口测试：验证请求校验、错误码、鉴权和响应契约。
- 端到端测试：覆盖关键业务闭环，不替代下层测试。

### 9.2 ArchUnit 强制规则

后端业务模块应逐步建立并持续通过以下规则：

- `domain..` 不依赖 Spring、MyBatis、Dubbo、Sa-Token、Redis、`interfaces..` 或 `infrastructure..`。
- `interfaces..` 不依赖 Repository、Mapper 或具体 Adapter。
- Controller 只依赖 application 和协议 DTO。
- application 不依赖具体 infrastructure 实现。
- 应用端口接口放在 `application.port..`，不与用例实现放在同一个包。
- 聚合和领域对象不得被 Controller 直接返回。

### 9.3 测试可读性

- 测试名称使用中文 `@DisplayName` 或清晰的英文行为描述，必须表达场景和预期。
- 复杂测试按“给定、当、则”组织，并用中文注释解释非显而易见的准备条件。
- 每个修复必须有能够在修复前失败的回归测试。

## 10. 前端适用规则

前端不机械套用后端聚合和仓储分层，但必须遵守以下原则：

- 领域术语与 `GLOSSARY.md` 一致。
- 业务状态、接口 DTO、页面展示模型分离，避免组件直接拼装后端协议。
- 复杂业务流程集中在明确的 hook、context 或 domain module 中，组件主要负责交互和展示。
- 新增或修改的复杂组件、公共 hook、状态机及安全敏感逻辑必须添加中文注释，说明职责、输入输出和边界。
- 不给显而易见的 JSX、样式属性或简单事件转发添加噪声注释。
- 排版保持现有前端写法，不套用后端 Java 的大括号规则。两空格缩进，`{` 留在语句行尾；单行语句可以不加大括号。

## 11. 代码评审检查清单

交付前逐项确认：

- [ ] 新术语已写入 `GLOSSARY.md`，且代码命名一致。
- [ ] 限界上下文、聚合和事务边界明确。
- [ ] Controller、应用层、领域层和基础设施层没有越界逻辑。
- [ ] domain 没有依赖框架或基础设施。
- [ ] 跨上下文契约没有泄漏 Entity、聚合或框架对象。
- [ ] 关键模块的 Interface 足够小，复杂性被隐藏在实现中。
- [ ] 关键类、公开方法，以及含有业务判断的私有方法具有准确的中文注释；不能只有类注释。
- [ ] 方法体内只在复杂逻辑处说明原因。并发、事务、安全和外部调用存在必要的中文说明。
- [ ] 没有逐行翻译代码、给易懂调用添加的噪声注释、失效注释或包含敏感信息的注释。
- [ ] 新增和修改的行为有相称的自动化测试。
- [ ] ArchUnit 和模块测试通过。
- [ ] 相关 PRD、接口文档和 ADR（如有）已同步更新。
- [ ] 后端 Java 代码块的 `{` 在行尾、`}` 单独成行。前端仍使用现有前端排版，未套用 Java 大括号规则。
- [ ] 数据库读写使用 MyBatis-Plus，Mapper 与 Wrapper 没有泄漏到 domain、application 或 interfaces。仓储实现类名不带 MyBatis 前缀。
- [ ] 领域对象与 Entity、应用视图、跨上下文契约之间的结构转换使用 MapStruct。转换器类名以 Converter 结尾，domain 不依赖 MapStruct，聚合没有为转换增加 setter。
