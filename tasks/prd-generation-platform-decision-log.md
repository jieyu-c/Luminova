# Luminova 生成平台架构讨论与决策日志

> 本文档是生成平台后续讨论的工作台，用于记录待确定问题、备选方案、决策依据和最终结论。  
> 已确认的稳定结论应同步回主文档：[统一生成平台架构 PRD](prd-generation-platform.md)。

## 1. 文档目标

- 按合理顺序逐项确定生成平台设计；
- 区分“已决定”“待讨论”和“暂缓决定”；
- 保留关键方案的选择理由及被否决原因；
- 防止框架、数据库和接口设计先于领域模型；
- 为后续实现提供可追溯的架构决策。

## 6. TOPIC-01：领域模型

### 需要确定

- Job 是一次用户意图，还是一次具体执行？
- 一个 Job 首期是否始终包含至少一个 Step？
- 手动重试是在原 Job 下创建 Attempt，还是创建新 Job？
- 自动重试属于同一 Step 的新 Attempt 吗？
- Artifact 归属于 Job、Step、Attempt 中的哪一层？
- 一个 Step 是否允许产生多个 Artifact？
- 用户从多个结果中选择“当前结果”的关系存放在哪里？
- 导出任务和 AI 生成任务是否使用完全相同的 Job 模型？

### 最终模型

```text
Job       一次不可变的用户意图
Step      Hub 为完成 Job 规划的执行单元
Attempt   Step 的一次真实派发和执行
Artifact  Attempt 产生并进入平台存储的不可变产物
```

四个对象分别作为独立一致性边界：

```text
GenerationJob       聚合根
GenerationStep      聚合根
GenerationAttempt   聚合根
GenerationArtifact  聚合根
```

逻辑上 Job 拥有完整任务，但不整体加载 Step、Attempt 和 Artifact 集合。Hub 应用服务在同一有界上下文和数据库事务内协调这些聚合。

### 已决定的关系

- 一个 Job 至少包含一个必要 Step；
- 一个 Step 可以有多个历史 Attempt，但同一时间最多一个活动 Attempt；
- 一个 Attempt 可以产生多个 Artifact；
- Artifact 必须记录来源 Job、Step 和 Attempt；
- Step 依赖未来使用独立关系表达，不使用单个 `dependsOn` 字段；
- Job 输入、来源版本和协议版本创建后不可修改；
- Artifact 内容、Storage Key、来源和校验和创建后不可修改。

### 重试语义

| 场景 | 决策 |
|---|---|
| 系统因临时错误自动重试 | 原 Job、原 Step 下创建新 Attempt |
| 用户点击重试且输入不变 | 创建新 Job，通过 `retryOfJobId` 关联 |
| 用户修改输入后再次生成 | 创建新 Job，通过来源链关联 |
| 未来从失败步骤恢复 | 创建新 Job并引用旧 Job 可复用产物 |

Job 终态不重新打开。这样可以保持用户意图、成本、错误和结果历史清晰可审计。

### 当前结果归属

```text
Generation 服务：保存所有历史 Artifact
Canvas 服务：保存 currentArtifactId、sourceJobId 和 nodeVersion
```

迟到结果仍登记为 Artifact，但如果节点版本已经变化，Canvas 不自动切换当前产物。

### 必须防止

- 将 Job 与供应商任务 ID 等同；
- 将系统重试和用户再次生成混为一类；
- 重试时覆盖旧 Attempt 的请求、响应或错误；
- 将当前选中结果覆盖历史 Artifact；
- 让 Worker 创建 Job 或直接写 Hub 任务表；
- 将所有对象做成每次整体加载和保存的巨大聚合。

### 最终决策

已决定，详细属性、不变量和事务边界见主 PRD 第 8 章。

## 10. TOPIC-05：统一 API 与任务协议

### 已初步确定

- OpenAPI 3.1 描述 HTTP API；
- JSON Schema 2020-12 描述任务参数；
- 使用 `taskKind + oneOf/discriminator`；
- 公共信封与具体强类型 `input` 分离；
- 保存 `specVersion`；
- 不直接透传供应商请求。

### 仍需确定

- 首期是否从 OpenAPI 自动生成 Java DTO；
- Java DTO 与 JSON Schema 谁是协议源文件；
- Schema 与代码如何做兼容性检查；
- `metadata` 允许哪些字段；
- `execution` 中哪些选项允许用户控制；
- `modelProfile` 是用户可见还是平台内部字段；
- 首期各 TaskKind 的完整输入 Schema。

### 最终决策

部分确定，详见主 PRD第 10 章。

### DEC-015：四类领域对象采用独立一致性边界

- 日期：2026-06-25
- 状态：已决定
- 关联主题：TOPIC-01

#### 背景

现有 `GenerationTask` 将用户意图、内部步骤、供应商执行和结果混在同一个对象中，难以表达多步骤、自动重试、历史产物和高频进度更新。

#### 备选方案

1. 保留一张 Task 表，通过 JSONB 扩展；
2. Job 作为巨大聚合，内部持有所有 Step、Attempt 和 Artifact；
3. Job、Step、Attempt、Artifact 分别作为独立一致性边界。

#### 最终决策

选择方案 3。逻辑上 Job 拥有整个任务，持久化与并发上四个对象分别作为聚合根，由 Hub 应用服务协调。

#### 决策理由

- 避免高频进度事件争抢同一个巨大聚合；
- 避免加载不断增长的执行历史；
- 保留每次执行和每个产物的完整审计；
- 支持首期单 Step 和未来多 Step；
- 便于按不同生命周期设置索引和数据保留策略。

#### 影响

- API：前端以 Job 为主要查询对象；
- 数据库：至少拆为 Job、Step、Attempt、Artifact 四张核心表；
- 消息：Command 必须定位到 Job、Step 和 Attempt；
- 运维：可独立查看每次真实执行；
- 成本：成本可以精确归属 Attempt。

#### 重新评估条件

不预计回退为单表模型；若未来引入专用工作流引擎，可重新评估 Step 的持久化归属，但保留外部 Job 和执行历史语义。

### DEC-016：自动重试创建 Attempt，用户重试创建 Job

- 日期：2026-06-25
- 状态：已决定
- 关联主题：TOPIC-01、TOPIC-10

#### 背景

系统临时错误重试和用户主动再次生成的语义不同。将两者都建模为 Task 重试，会导致输入快照、终态和成本历史模糊。

#### 最终决策

- 系统自动重试：原 Job、原 Step 下创建新 Attempt；
- 用户手动重试或修改输入后再次生成：创建新 Job，并通过 `retryOfJobId` 和 `rootJobId` 关联。

#### 决策理由

- Job 输入保持不可变；
- 终态 Job 不重新打开；
- 用户可以比较每次生成结果；
- 自动重试成本和供应商错误保留在同一 Step；
- 修改输入与不修改输入遵循同一用户操作模型。

#### 影响

- API：手动重试返回新的 Job ID；
- 数据库：Job 需要重试链字段；
- 消息：自动重试生成新的 Attempt Command；
- 运维：可以区分平台重试与用户再次生成；
- 成本：自动重试和新 Job 成本分别统计。

#### 重新评估条件

未来若产品要求“原地重试并保持同一 Job ID”，必须先评估终态重开、缓存、事件订阅和审计语义的复杂度。

### DEC-017：Artifact 不可变，当前产物引用归 Canvas

- 日期：2026-06-25
- 状态：已决定
- 关联主题：TOPIC-01、TOPIC-09

#### 最终决策

Generation 保存全部历史 Artifact；Canvas 保存节点当前选择的 `currentArtifactId`、`sourceJobId` 和节点版本信息。

#### 决策理由

- 生成历史不会因重新生成而丢失；
- 迟到结果不会覆盖用户正在编辑的新版本；
- 同一个 Artifact 可以被导出或后续步骤复用；
- Generation 不需要理解画布当前选择逻辑。

#### 重新评估条件

如果未来建立独立的 Asset 服务，可将 Artifact 的长期资产管理迁移出去，但 Generation 仍需保留来源与结果引用。
